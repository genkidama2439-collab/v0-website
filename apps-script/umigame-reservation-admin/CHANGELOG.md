# 変更履歴

## 2026-08-20

### まるごと1日セットが海亀1行だけになる不具合

本番の`予約一覧`を調査し、V列（現在の`メールアドレス`列）全体に、旧
`LINE送信確認`列のチェックボックス入力規則が残っていることを確認した。
診断ログには、メールアドレスをV列へ書く際の入力規則違反が記録されていた。
このため45列の通常保存が失敗し、暫定の縮小書き込み経路でC5/C6の先頭にある
海亀行だけが残っていた。

対応:

- 本番シートV列の誤った入力規則を、セル値や書式を変えずに除去
- 影響を受けた9月21日の実予約を同じ予約番号のGoogleカレンダー3予定と照合し、
  海亀11:00（11,333円）・SUP12:30（11,333円）・ナイト19:20（11,334円）の
  3行、合計34,000円へ復元
- スキーマ版を`2026.08.20-1`へ更新し、V〜ASの不要な入力規則を自動除去
- 新規行の書き込み直前にもV〜ASの入力規則を除去し、挿入行が古い規則を
  継承しても予約保存を妨げないようにした
- 保存直後に予約番号・時間・プラン・金額を再読込して検証
- 同じ予約番号が一部の行しか持たない場合、重複成功扱いを禁止
- 入力規則残存・不完全な重複・正常な再送の回帰テストを追加

本番反映状況:

- 本番シートの入力規則修復と影響予約の復元: **完了**
- 恒久対策を含む`Code.gs`: **本番GASへの再デプロイ待ち**

## 2026-08-14

### プランの振り分けを`planId`優先へ修正（全体監査で発見）

備考欄（`specialRequests`）にはお客様の自由記述がそのまま入るのに、セットプランの
振り分けがその文字列を検索して決まっていた。そのため要望欄に書かれた言葉だけで
別プラン扱いになり、シートの行数・Googleカレンダーの予定・管理者メールの内訳が
実際の予約と食い違っていた。

実際に起きうる誤りと影響:

| 予約 | 要望欄の記述 | 修正前の扱い | 影響 |
|---|---|---|---|
| 昼夜セット C1/C2 | ドローンSUP | まるごと1日セット | 実在しないドローンSUPの行・カレンダー予定が作られる |
| 海空セット C3/C4 | ヤシガニ / ナイト | まるごと1日セット | ナイト開始時刻を取得できず`doPost`が失敗し、**予約自体がエラーになる** |
| 通常セット C1/C3/C5 | 貸切 | 貸切セット | 売上内訳が貸切単価で分割される（合計金額は変わらない） |
| 単品 S1〜S8 | `[COMBO booking]` | 海空セット | 単品予約が2行に分割される |

修正内容:

- サイトが常に送っている`planId`（S1〜S8 / C1〜C6）を最優先で使う
  `bookingPlanId_()` を追加し、`isSeaSkyComboBooking` / `isComboBooking` /
  `isPrivateComboBooking_` / `c5c6IsTripleBooking_` / `c5c6IsPrivateTriple_` が
  これを先に見るようにした
- `planId`が取れない古い送信・手動再送のときだけ、従来のテキスト判定へフォールバックする
- 金額・行の作り方・メール本文・カレンダー本文の組み立ては変更していない
- リポジトリ側に回帰テスト `lib/gas-plan-routing.test.mjs` を追加し、
  要望欄に上記の語を書いてもプラン振り分けが変わらないことを`npm test`で検査する

本番反映状況

- **反映済み（2026-08-14・ユーザー確認）**。`Code.gs`貼り替え＋新バージョンでのウェブアプリ再デプロイまで完了
- `setupSheet()`は実行していない

### `LineSafeSend.gs`を削除

- 内容が`Code.gs`末尾（LINE安全送信ブロック）と完全に同一だった
- 両方を同じGASプロジェクトへ貼ると`sendLineNotify`等のラップが二重に適用され、
  1回の送信で`LINE送信履歴`へ2行記録される事故になるため、重複ファイルを廃止
- 本番のGASプロジェクト側には元から`Code.gs`だけを貼る運用のため、動作への影響はない

### 予約再送の重複登録・大量メール防止（`2026.08.14-5`）

- 同じ入力内容の再送で同じ予約番号を使えるよう、サイト側の送信IDと連携
- GASのスクリプトロック内で予約番号を照合し、登録済みならシート・カレンダー・管理者メールを再実行しない
- 予約番号B列の最終データ行へ追記し、空行T列の`FALSE`によって1000行目へ飛ぶ問題を修正
- 空行T/Uの不要値だけを初回修復時に除去し、実予約行のLINE状態は保持
- `setupSheet()`によるT列全消去を廃止
- 管理者メールへお客様のメールアドレスを追加

## 2026-08-01

### 合計受取金額の表示

管理者メール・Googleカレンダーとも、金額の計算ロジックは変更していません。表示のみの変更です。

管理者メール

- 【予約内容】の`合計金額`を`合計受取金額`へ変更（単体プラン・全セット共通）
- クーポン利用時は`（通常料金 ¥X − クーポン ¥Y）`の内訳行を追加
- 海空セット・昼夜セット・まるごと1日セットの売上内訳の末尾へ`合計受取金額`を追加
- 内訳末尾の合計は`totalPrice`の再表示ではなく、内訳各行の実額を合算して算出
- 内訳の`/ クーポン-¥X`を`（クーポン適用済 -¥X）`へ変更し、二重減算の誤読を防止

Googleカレンダー

- 単体プランの`売上`へ`（クーポン適用後・当日この金額を受け取る）`を付記
- セットの各イベントへ【セット全体の受取金額】ブロックを追加（合計・担当ごとの内訳）
- セットの`売上`へ`（このツアー分の計上額）`を付記
- 現金の受取担当を「開始時刻が最も早いツアー」に決定し、該当イベントのみ`← このツアー開始時に全額受け取る`と表示
- 他のイベントは`（受取済み・このツアーでは受け取らない）`と表示し、二重受取を防止

検証

- `Code.gs`単体・`TestMail.gs`結合ともJavaScript構文検査に合格
- 模擬環境でメール6パターン（単体×クーポン有無／海空／昼夜／まるごと1日／端数）を確認
- 模擬環境でカレンダー4パターン計8イベントを確認し、内訳合計と受取額の一致、受取担当が各セット1イベントのみであることを確認
- `TestMail.gs`を追加（`testReceiveTotalEmail`で管理者メールの表示確認。シート・カレンダー・LINEには影響しない）
